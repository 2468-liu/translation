# samples/PARTIAL_QUALITY.md

`#4` 的回看清单：partial 250ms vs 750ms，**只看 partial 阶段的文本质量**。

与 `BUCKETING.md` 分开是因为那是另一件事——那是四桶体感分桶（完整一遍、人眼回看），
这里只盯一句话说完之前屏上出现过什么。混在一个文件里，将来分不清是体感问题还是 partial 质量问题。

## 看哪一段时间

```
句子开始说  →  end 事件之前
```

**end 之后不看。** 那是最终译文，不是 partial。

## 怎么对比两格

**不是"250 有几处问题、750 有几处问题"**——基数不同，没法比。

是**同一句，两格并排看**：

```
句子 1
  250ms:  'Hi! Hi, how ar'        ← 截断
  750ms:  'Hi! Hi, how are you?'  ← 完整
  → 750 更好

句子 2
  250ms:  'Hot!'
  750ms:  'Hi!'
  → 两个都不完整，但 750 的词对；250 是认错了词
```

**逐句对比，不做汇总。** 汇总会掩盖"哪类句子有问题"。

## 每句记三个问题

只看屏上"整句说完之前"**最后出现过的那一版文本**：

1. **漏词** —— 句子说完后原文里有这个词，partial 里没有
2. **错字** —— partial 里有个词，但明显不是原话
3. **截断** —— partial 停在半个词/半句话上

**每句各记 有/无。不记"严重程度"** —— 那个会变成"我觉得"。

## 表格

| 句子 | 250ms partial | 750ms partial | 谁更好 |
|---|---|---|---|
| | | | |

## 结论规则（跑之前定好）

```
750 更好的句子数 > 250 更好的句子数   → 选 750
250 更好的句子数 > 750 更好的句子数   → 选 250
平局                                → 看功耗/温度/风扇
```

## 不要做

- 不测延迟（那是另一件事）
- 不看 end 之后的文本
- 不记"严重程度"或 1~5 分
- 不在没有对照的情况下说"750 好像更好"

## 这份清单自己的极限

看 partial 的时候你已经知道原文是什么——人工评估里这叫**泄漏**。

但这不构成问题：**这里要判断的不是"识别准确率"这种客观指标，是"哪个更完整"。**
主观就主观，不要假装客观。

**而且如果差异很明显，你根本不需要填表**——看一眼就知道选 750。
这张表是给"不确定"时用的，不是每句都要填。

## 为什么值得做

TTS 最干净的条件下，CT2 small 在短窗口上**没有一次给出完整正确的输出**：

```
0.3s  → 空          （large 出 'You'）
0.6s  → 'Hot!'      （large 出 'Hi'，认错了词）
1.3s  → 'Hi! Hi, how ar'  （截断，large 出完整句）
```

而管线喂给 ASR 的恰恰就是这种窗口。**750ms 让每次 partial 的音频更长，
很可能顺带改善 partial 文本质量** —— 所以 #4 可能有双重收益，不只是省电。

顺带记一句已经确定的：**这不是 `language=auto` 造成的**。
三方对照下 `small auto` 与 `small en` 输出逐字相同，auto 只是把置信度从 1.00
变成 0.44~0.90。
